# P0 · 오케스트레이터 시제품

설계안(실시간 동시처리 언어 모델 설계안, 가칭 Stream-Mind v3)의 로드맵 첫 단계다.

> P0 · 오케스트레이터 시제품: 기존 소형 하이브리드 모델 + 이벤트 루프 + 상태 포크, 모델 수정 없음.
> 실시간 텍스트 게임 환경 구축, 턴 방식과 비교. **관문 1: 실시간 점수가 턴 방식보다 높음.**

## 1. 구조

```
           ┌──────────────────── 모델 (안) · Mind ────────────────────┐
           │ 원 스트림: 깨우기 · 사고 · 결론(intent)                    │
           │ 빠른 분기: 상태 포크 → 호출 하나 → 버림                     │
           │ 내부 상태: Backend 상태 (HF 캐시 / 시뮬레이션 계획)          │
           └──────────────┬──────────────────────────▲────────────────┘
                     호출 │ RiskGate (등급 0/1/2)       │ 관측 · 알림 (신뢰 등급)
           ┌──────────────▼──────────────────────────┴────────────────┐
           │ 도구 규격: 설명서 · 호출 · 관측 · 알림 · 신뢰 등급 · 마감     │
           ├────────────┬────────────┬────────────┬───────────────────┤
           │ 메신저      │ 터미널      │ 게임        │ 노트 (외부 기억)    │
           │ 지시(인증)  │ 데이터      │ 데이터      │ 데이터             │
           └────────────┴────────────┴────────────┴───────────────────┘
```

### 스트림 형식 (1단계 표현)

```
[T=12.000]<obs tool=game trust=data kind=frame>…프레임…</obs>
<think>d=9 계획 UUSUUUUUU 가치 9.0 / 결론: 계획 확정</think>
[T=12.950]<call tool=game op=act origin=fork status=executed>U</call>
[T=13.100]<obs tool=messenger trust=instruction kind=result>user: 지금 몇 점이야?</obs>
<wait>
```

- 도구 이름은 태그 속성값일 뿐 모델 어휘가 아니다. 새 도구는 `Tool` 규격만 지키면 붙는다(G10).
- 데이터 관측 속에 `<obs …>`, `<call …>`, `[T=` 같은 문자열이 있어도 태그로 해석되지 않게 바꿔 넣는다
  (`stream.sanitize`). 터미널 출력이 지시인 척하는 것을 막는 첫 번째 장치다.
- 스트림 기록은 최근 N개 이벤트만 메모리에 둔다(세션이 길어져도 메모리가 늘지 않음, G5).

### 깨우기와 마감 (핵심 모듈 2)

`Mind.step()`은 다음 중 하나일 때만 모델을 돌린다. 아니면 다음 사건 시각까지 잠든다.

1. 도구 알림 (새 메시지, 새 프레임, 명령 종료, 정보가 담긴 호출 결과)
2. 마감 임박: 마감까지 남은 시간 ≤ 사고 한 번 + 관측 주입 + 앞선 분기들 + 이 분기의 지연
3. 사고가 수렴하지 않았고 사고 예산이 남음

- 마감이 임박하면 원 스트림의 사고 토큰을 줄여(시간 압박 → 짧은 사고) 분기가 마감 전에 나가게 한다.
- 사고 예산을 다 쓰고도 수렴하지 않으면 남은 질문을 노트에 `unresolved`로 적고 잠든다.
- 마감은 hard(게임 프레임: 늦으면 무의미, 기본 행동에 맡김)와 soft(사용자 응답: 늦어도 보냄)로 나뉜다.
- 턴 모드는 특수한 경우다: 입력이 한 번에 오고 마감이 없으면 수렴할 때까지 생각한 뒤 답한다
  (`test_turn_mode_is_a_special_case_of_the_stream`).

### 상태 포크 (핵심 모듈 3)

- 포크는 `think` 호출 사이, 즉 원 스트림이 토큰을 다 만든 경계에서만 연다.
- 행동은 언제나 분기에서만 나간다. 원 스트림이 사고 안에서 결론 낸 호출(`<call>`)도 분기를 통해 나간다.
- 분기가 낸 호출은 원 스트림에 `<call … origin=fork status=…>` 실행 기록으로 들어가고, 원 스트림은
  다음 실행에서 이를 관측해 계획을 고친다. 분기는 버린다.
- 분기 직전에 도구를 한 번 더 폴링해, 분기가 사고하는 동안 들어온 가장 새로운 관측을 보게 한다.

### 행동 위험 등급 (핵심 모듈 5)

| 등급 | 예 | 실행 조건 (`RiskGate`) |
|---|---|---|
| 0 | 게임 행동, `ls`/`cat`/`git status`, 중단 신호, 메시지 보내기, 노트 검색·추가 | 분기에서 바로 |
| 1 | `mkdir`/`cp`/리다이렉트, `pip install`, `git commit`, 노트 갱신·삭제 | 원 스트림이 결론 낸 호출일 때만 |
| 2 | `rm`, `curl`, `chmod`, `git push`, `sudo`, 스크립트·인터프리터·`$(…)`, 모르는 명령 | 결론 + 메신저로 인증된 `/confirm 번호` |

- 복합 명령(`;`, `&&`, `|`)은 가장 높은 등급을 따른다. 해석할 수 없으면 등급 2.
- 샌드박스 터미널은 한 단계 낮춘다.
- 확인 요청은 메신저로 나가고, 인증되지 않은 발신자의 `/confirm`은 무시한다.
- `MindStats.unsafe_executions()`는 숙고 없이 실행된 등급 1+, 확인 없이 실행된 등급 2 호출 수다(G9: 항상 0).
- `MindStats.unexplained_actions()`는 대응하는 사고 기록 없는 행동 수다(G8).

## 2. 백엔드

| 백엔드 | 무엇 | 용도 |
|---|---|---|
| `PlannerBackend` | 언어 모델이 아니다. 사고 토큰 16개 = 빔 탐색 한 단계인 "생각할수록 나아지는" 계획기. 같은 첫 행동이 3단계 되풀이되면 수렴(PUMA식). 분기는 미완성 계획을 엿보고(AgileThinker식), 계획이 지금 프레임과 안 맞으면 한 단계 반사로 고른다. | 관문 1 측정, 제어 논리 검증 |
| `ScriptedBackend` | 정해 둔 사고를 순서대로 낸다 | 단위 테스트 |
| `HFBackend` | 공개 소형 하이브리드 체크포인트를 수정 없이 사용. 탐욕 디코딩, 캐시 깊은 복사로 포크, 후보 로그 확률로 행동 선택 | 실제 모델 위에서 동작 확인 |

모드: `stream` 이 설계 / `turn` 턴 방식 / `no-fork` 포크 끔 / `fixed-tick` 이벤트 구동 끔 / `reflex` 사고 끔.

**판정: 통과.** 판정 기준은 "모든 압박에서 stream ≥ turn, 사고가 프레임을 넘기는 압박(> 1)에서 stream > turn"이다.
압박 ≤ 1에서는 사고가 한 프레임 안에 끝나 두 방식이 같은 행동을 하므로 동률이 정상이다.

읽을 거리:

- **포크의 기여**: `no-fork`는 압박이 커지면 `turn`과 비슷하게 무너진다. 사고가 끝나야 행동하는 한 낡은 관측으로 움직이기 때문이다.
- **사고의 기여**: 압박 2~4에서 `stream`이 `reflex`보다 높다. 분기가 원 스트림의 미완성 계획을 엿보는 효과다.
  압박 8에서는 계획이 거의 완성되지 못해 `stream`이 `reflex` 수준으로 내려간다.
- **이벤트 구동의 기여**: 점수는 `fixed-tick`과 같지만, 압박이 낮을수록 토큰 사용이 크게 준다(압박 0.25에서 26 대 898 tok/s).
- **G3의 "압박이 커질수록 격차 확대"**: snake는 성립(+9.3 → +13.1 → +14.1). freeway는 압박 8에서 격차가 줄었는데,
  turn이 이미 0점에 닿은 바닥 효과다. 관문 판정에는 넣지 않고 벤치마크 출력에 추세로만 보여 준다.

## 4. 실제 모델 연기 시험

`examples/hf_smoke.py`, `Qwen/Qwen3.5-0.8B`(Gated DeltaNet 하이브리드), CPU 4코어, float32,
`flash-linear-attention`/`causal_conv1d` 없이 PyTorch 참조 구현. 게임 프레임 6초, 메신저 응답 마감 20초.

| 항목 | 측정 |
|---|---|
| 상태 포크 (캐시 깊은 복사) | 문맥 100 / 1,000 / 3,000 토큰에서 6.6 / 5.8 / 10.9ms |
| 사고 토큰 하나 | 약 120~150ms |
| 분기 (게임 후보 3개 점수 매기기 + 실행 기록 주입) | 약 2.3~2.5초 |
| 동작 확인 | 관측 주입, 사고 생성, 포크, 후보 점수 매기기, 메신저 열린 행동 생성, 검문 위반 0, 사고 기록 없는 행동 0 |

- 포크 비용이 문맥 길이와 거의 무관하다는 설계안의 전제(선형 층 상태가 고정 크기)를 실제 체크포인트에서 확인했다.
  일반 어텐션 층의 KV 때문에 조금씩은 늘어난다. 슬라이딩 윈도·attention sink 적용은 P2의 일이다.
- 처음 구현은 마지막 로짓을 전체 로짓 텐서의 뷰로 들고 있어 포크가 문맥에 비례해 느려졌다(3,000 토큰에서 3.5초).
  마지막 위치만 복사하고 `logits_to_keep=1`을 써서 고쳤다.
- 모델이 스트림 형식을 학습하지 않았으므로 사고와 메시지 내용은 의미가 없다(스트림 형식을 흉내 내는 수준).
  CPU 참조 구현이라 몇몇 프레임 마감은 놓친다. 품질은 P1(스트림 변환 SFT), 속도는 GPU와 최적화 커널(G6)의 일이다.

## 5. 한계와 다음 단계

P0에서 의도적으로 하지 않은 것:

- **원 스트림과 분기의 한 배치 실행.** 지금은 사고 → 분기를 차례로 돈다. 같은 가중치라 한 배치로 돌릴 수 있다는 설계는
  아직 구현하지 않았다. 현재 방식은 지연을 비관적으로 잡는 쪽이다.
- **메신저 `auto_read`.** 학습 전 모델은 알림을 보고 `read`를 부를 줄 모르므로 P0 비계가 대신 부른다(`CallLog.scaffold`).
  설계대로라면 알림을 언제 읽을지는 모델이 정한다. 도구 사용법 학습(P1·P4) 뒤 끈다.
- **시간 임베딩, 스트림별 위치 인코딩**(2단계 표현), **슬라이딩 윈도·sink**, **빠른 가중치·어댑터**, **유휴 학습**, **RL**:
  P1~P4의 일이다. 노트 도구는 출처 태그와 `training_material()`(믿을 수 있는 출처만)을 갖춰 P3 재료로 쓸 수 있게 해 두었다.
- **Overcooked**는 구현하지 않았다. Freeway와 Snake만 있다.

다음은 P1 · 스트림 학습이다: 0.5~2B 하이브리드 모델에 스트림 변환 SFT, 미래 정보 누설 검사.
관문 2는 정적 벤치 하락 없음 + 실시간 점수 추가 향상이다. P0의 `GameTool`, `TurnAgent`, `gate1`은
P1 모델을 `HFBackend`로 붙여 그대로 다시 쓸 수 있다.
